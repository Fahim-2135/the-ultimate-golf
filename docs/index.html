A. How the project is built

1 The files, and which one is the real game DOC

The project is five C files plus an assets folder.

  • the_ultimate_golf_game level_1.c … level_4.c — each level as its own complete program. Each one has its own main(), opens its own window and plays only that level. They are the place where a level is designed and tested.
  • the_ultimate_golf.c — the game you actually run. It contains all four levels joined together, plus the intro, the menu, the difficulty choice, the level briefing and the sound system.
  • assets/ — pictures (PNG) and sounds (WAV, MP3, OGG), in one folder per level.

The joined file is not typed by hand. A small Python script copies the four level files, renames everything inside them so their names cannot clash, and glues the game shell on top (section 101). So a level is edited in its own file, then the joined game is rebuilt from it.

Sizes: level files are 839–1351 lines, and the joined game is about 5900 lines.

2 Why the levels needed renaming (the l1_ l2_ l3_ l4_ prefixes) DOC

Each level was written on its own, so all four use the same names: ball, speed, reset_level, draw_hud, and so on. In C, two functions with the same name in one program is an error (“redefinition”).

The fix is mechanical: every name a level owns gets a prefix. ball becomes l2_ball, update_ball becomes l2_update_ball. Names belonging to raylib (DrawCircle, Vector2) are left alone, and so is text inside quotes.

The result is that all four levels live in one program without knowing about each other, and each keeps its own copy of the ball, the walls, the timers and the drawing code. The game shell then calls l1_update(), l2_update() and so on, depending on which level is being played.

3 How to build and run it DOC

The game is one C file compiled with GCC and linked against raylib:

  • E:/C/mingw64/bin/gcc.exe — the 64-bit compiler. The 32-bit one on the PATH cannot link this raylib build.
  • -I .../raylib/include — where raylib.h lives (the list of functions).
  • -L .../raylib/lib -lraylib — the compiled raylib library itself.
  • -lopengl32 -lgdi32 -lwinmm — Windows libraries raylib needs for graphics, windows and sound.
  • -Wall — turn on all warnings. The whole game compiles with zero warnings.

In VS Code this is the Build Raylib App task. The program must be started from the folder that contains assets, because it loads files by relative path, e.g. assets/beach/beach_crab.png.

4 raylib in one page DOC

raylib is a small C game library. Everything used in this project comes from five groups:

  • Window: InitWindow, WindowShouldClose, CloseWindow, SetTargetFPS, ToggleBorderlessWindowed.
  • Drawing: BeginDrawing / EndDrawing around every frame, then shape calls like DrawCircle, DrawRectangleRec, DrawLineEx, DrawRing, DrawPoly, DrawText.
  • Pictures: LoadTexture into video memory, DrawTexturePro to draw any part of it at any size and angle, UnloadTexture at the end.
  • Input: IsMouseButtonPressed, IsMouseButtonReleased, GetMouseX, IsKeyPressed.
  • Sound: InitAudioDevice, LoadSound + PlaySound for short effects, LoadMusicStream + UpdateMusicStream for long music that streams from disk.

raylib also ships raymath.h, which gives vector maths: Vector2Add, Vector2Scale, Vector2Length, Vector2Normalize, Vector2Reflect, Vector2DotProduct, Vector2Rotate, Clamp. The physics in this game is almost entirely those calls.

5 The game loop DOC

Every raylib program has the same shape: set up once, then repeat one frame at a time until the window closes, then clean up.

  • InitWindow creates the window; SetTargetFPS(60) asks raylib to wait at the end of each frame so the game runs at 60 frames per second.
  • while (!WindowShouldClose()) runs once per frame. SetExitKey(KEY_NULL) stops ESC from closing the window, because this game uses ESC to go back to the menu.
  • Inside a frame: first work out what changed (input, physics, timers), then draw the result between BeginDrawing() and EndDrawing().
  • At the end: unload pictures and sounds, then CloseWindow().

Drawing never changes the game state, and updating never draws. Keeping those apart is what makes it possible to run a level invisibly in the background (for the menu cards) or to simulate thousands of shots with no window at all (the test harness, section 98).

6 dt: why everything is multiplied by time APP

Watch it move: demo 6 in game_learn.exe

GetFrameTime() returns how long the previous frame took, in seconds. On a 60 FPS machine that is about 0.0167. The code calls it dt.

Speeds are stored in units per second, not units per frame. To move the ball for one frame the speed is multiplied by dt: ball = ball + speed*dt. If a frame takes twice as long, the ball moves twice as far, so the game runs at the same real-world speed on a fast or a slow computer.

One guard matters: if the window is dragged or the game stalls, a frame can suddenly take a whole second. The ball would then jump a huge distance and pass straight through a wall. So dt is capped:

if (dt>1.0/30) dt = 1.0/30;

Worst case the game slows down, but nothing ever teleports through a wall.

8 The u scale: designed for 1920x1080, fits any screen APP

Watch it move: demo 8 in game_learn.exe

Every position and size in the game is written as a number of design units, where the design screen is 1920×1080. A wall is 28 units thick, the ball has radius 7.

At startup the game works out one number, u, that converts design units to real pixels:

u = height/1080; if (width/1920 < u) u = width/1920;

It takes the smaller of the two ratios, so the whole course always fits, whatever the screen shape. On a 1920×1080 screen u is exactly 1. On a 1280×800 screen it is 0.667, so everything is drawn two thirds the size and the game plays identically.

Because speeds are also written in design units per second (110*u friction, 650*u top speed), the physics scales with the screen too. The game shell keeps its own copy of the same number called su, used by the menu, intro and briefing.

9 Why everything is a global variable DOC

The ball, its speed, every obstacle, every timer and the score are global variables at the top of each level, not passed around as parameters.

That is a deliberate style choice: the level is one self-contained machine, and any function in it (update_ball, draw_obstacles, send_ball_back) can read and change the state directly. The cost is that those functions only work on that level's state, which is exactly why joining four levels needed the renaming trick from section 2.

The benefit shows up in the tools: because the state is global, the test harness can place the ball anywhere, call update_ball 240 times a second with no window open, and check the result (section 98).

10 The raylib types used everywhere DOC

  • Vector2 — two floats, .x and .y. Used for positions, speeds and directions. The ball is a Vector2, so is its speed.
  • Rectangle — .x .y .width .height, with x,y being the top-left corner. Walls, belts, zones, doors and the moving crabs are rectangles.
  • Color — four bytes r,g,b,a. Written either as a list {232,185,35,255} or with GetColor(0xE8B923FF).
  • Texture2D — a picture living in video memory.
  • RenderTexture2D — a picture the game can draw into (used by the menu cards and the briefing close-ups, section 83).
  • Sound — a short effect held in memory. Music — a long track streamed from the file while it plays.

Screen coordinates: x grows to the right, y grows downward. That is why “up the screen” is a negative y speed.

11 Naming and comment habits DOC

The code follows a few simple habits, kept consistent across all four levels:

  • lower case names with underscores: radius_ball, send_ball_back, plank_timer.
  • a one-line comment above each block saying what it is for, in plain words: //the ball goes back to where it was shot from.
  • braces on their own lines, and short if statements written on one line.
  • timers count in seconds and are named ..._timer or ..._clock; states are plain ints with a comment listing what each number means.

There are no structs, no pointers beyond what raylib needs, and no dynamic memory. Every array has a fixed size known at compile time, e.g. Rectangle walls[13];.

19 Friction: slowing down along the direction of travel APP

Watch it move: demo 19 in game_learn.exe

Friction takes a fixed amount of speed away every second, no matter which way the ball rolls:

  • measure the current speed: ball_speed = Vector2Length(speed)
  • subtract: new_speed = ball_speed - friction*dt
  • if that goes below zero, stop; otherwise scale the speed vector by new_speed/ball_speed, which shortens it without turning it.

Because the slowdown is constant, a ball rolls a distance of v²/(2·friction). With the normal 110 units and top speed 650, that is about 1900 units — roughly the width of the screen, which is how the levels were sized.

Then a stop threshold: under 6 units per second the speed is set to exactly zero. Without it the ball would creep forever at microscopic speed and you could never take the next shot, because shooting requires speed == 0.

21 Four sub-steps per frame, and why APP

Watch it move: demo 21 in game_learn.exe

A frame is 1/60 s. At top speed the ball would move about 11 units in one frame. Thin obstacles (a laser beam is 8 units, a crane beam 18) could be skipped entirely: the ball would be on one side before the step and past it after, and the collision test would never see it. That bug is called tunnelling.

The fix is to split each frame into four equal steps:

for (int i=0; i<4; i++) { update_obstacles(dt/4); update_ball(dt/4); }

Now the biggest move per test is under 3 units, smaller than any obstacle in the game, so nothing is missed. Obstacles are advanced in the same loop so that moving parts and the ball stay in step.

Combined with the dt cap from section 6, this is what makes the physics safe on any machine.

24 The reflect formula APP

Watch it move: demo 24 in game_learn.exe

The bounce itself is one raylib call: speed = Vector2Reflect(speed, normal), which computes v - 2(v·n)n.

In words: split the speed into the part along the wall and the part into the wall, then flip only the part going into the wall. The sideways part is untouched, so a ball hitting at a shallow angle skims along, and a ball hitting head-on comes straight back. No energy is lost, which is why the ball keeps its speed through a bounce and only friction slows it.

Three separate versions of the same bug were found by the automatic test, never by playing:

Planets and the black hole pull with a strength that fades to nothing at the edge of their field:

closeness = 1 - distance/field; pull = strength * closeness²

86 The cover-up trick (foam, doors, shadows) DOC

Several effects are done by drawing something and then covering the part you do not want:

  • Foam is drawn round all four edges of each sand piece, then the sand is drawn on top, so foam only remains where the neighbour is water.
  • Doors are drawn before the walls, so the part that has slid into the wall disappears behind it.
  • Shadows are the same sprite drawn first, offset and tinted black.

Each of these replaces code that would otherwise need to know which edges are exposed or how far a door has slid.

raylib's DrawText takes a top-left corner, so centring means measuring first:

DrawText(s, x - MeasureText(s,size)/2, y, size, colour);

Every important label is drawn twice, once in black a few units down-right and once in colour, which is the cheapest possible drop shadow and is what keeps the HUD readable over busy backgrounds. 90 The title slam APP

Watch it move: demo 90 in game_learn.exe

The title does not slide in, it lands. For the first 0.15 s it is drawn 3.5× too big and see-through, shrinking to its real size:

101 join.py: how the four levels become one program DOC

The joiner does five things per level:

  1. read the level file and drop its #include lines;
  2. collect every name it declares at top level (globals, #defines, functions) with a regex;
  3. rename those names with an lN_ prefix, skipping anything after a dot (struct fields) and anything inside quotes;
  4. apply the game-wide edits: stroke limit becomes a variable, top speed 520→650, shot power 2.5→3.125, obstacle timers multiplied by obstacle_speed, ESC text changed to "ESC menu";
  5. cut main() into start / update / draw / unload, and generate background_step and draw_scene.

Then it writes the shell around them. Editing a level file and re-running the joiner rebuilds the whole game, so the level files stay the single source of truth.
